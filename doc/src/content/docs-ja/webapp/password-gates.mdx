## 機能の contract

password protection はプロジェクトごとに設定し、default は off です。これは public site
全体の前に置く shared preview gate であり、account login ではありません。gate が有効な
場合、実在する static asset への request も含め、すべての content request は artifact
lookup、byte delivery、cache read より先に authorization を通過しなければなりません。

project password は plaintext で保存しません。private control boundary が slow、salted、
per-project verifier を保存し、pepper や signing secret を採用する場合はそれらも所有します。
multi-tenant public Worker は password verifier、tenant secret、shared password secret、
signing secret、D1 access、write capability を持ちません。narrow private authorization
service を呼び出し、返された capability を pinned public key で検証することだけができます。

## 有効化、rotation、無効化

webapp はプロジェクト単位の action とその結果を明示します。

- **Enable:** default-off state から新しい shared password を受け取り、private
  per-project verifier を導出・保存し、gate epoch を increment して、以後のすべての site
  request に authorization を要求します。
- **Rotate:** verifier を置き換え、epoch を increment し、以前の epoch で発行したすべての
  capability を invalidate します。既存の visitor は新しい password を入力し直します。
- **Disable:** private verifier を削除または deactivate し、epoch を increment して、
  outstanding capability を invalidate し、通常の public serving/cache policy に戻します。

UI は保存済み password を表示または復元してはなりません。変更対象のプロジェクトを
確認し、rotation または disable によって以前の capability cookie で得た access が終了
することを説明します。gate change は serving access に作用し、immutable project URL や
publication artifact は変更しません。

## Visitor の flow

有効な gate に対して、public Worker は content を配信する前に exact host と current
project gate state を解決します。current valid capability を持たない visitor には
platform-owned password form を返します。narrow login `POST` は入力された password を
private verifier service に送り、存在しない project と誤った password には同じ generic
denial を返します。

verification に成功すると、immutable project ID、exact public hostname、current gate
epoch、issued/expiry time、random token ID に binding された short-lived signed capability
が返されます。public Worker は pinned public key で capability を検証し、`Secure`、
`HttpOnly`、`Path=/`、`SameSite=Strict` を持つ host-only `__Host-` cookie に保存します。

valid signature だけでは不十分です。すべての request で byte/cache より先に current
project/gate authorization を確認し、capability の host、project、epoch、time bound が
現在も有効であることを検証します。password submission には body-size limit と rate
limit を適用し、project の存在を明かさずに、選択済みの slow verifier で比較します。

## Security と cache の動作

gate-before-bytes と gate-before-cache は release invariant です。認証に成功した visitor
が warm した public response を unauthenticated visitor が再利用できてはなりません。
そのため V1 は cookie ごとの cache partition を試みず、authorized artifact byte を含む
すべての gated response で shared cache を bypass します。

login page、denial response、login `POST` response、authorized gated content は
`no-store` です。gated artifact response には `Cache-Control: private, no-store` と
`CDN-Cache-Control: no-store` の両方を設定します。Worker は `cache.put` を呼ばず、
cache rule がこの policy を上書きしてはなりません。`Vary: Cookie` は defense in depth
であり、cache の許可ではありません。platform gate page/response は入力 password を
表示・log せず、search indexing も防止すべきです。

epoch change により、古い capability の expiry 前でも即時に logical revocation できます。
public Worker は tenant credential に関して secrets-free のままであり、responder compromise
の影響を限定します。

## Shared-password access の限界

gate が証明するのは、visitor がプロジェクトの current shared password を知り、対応する
short-lived capability を保持していることだけです。visitor account や durable visitor
identity は作成しません。この機能には visitor role、person ごとの permission、individual
revocation、visitor list、visitor audit trail はありません。

shared password を受け取った人は別の人に伝えられます。rotation は全員に対して古い
shared capability epoch を revoke しますが、visitor 1 人だけを選んで削除することは
できません。named collaborator、individual access control、auditable access が必要な
プロジェクトには別の将来機能が必要であり、この gate にその役割を持たせてはなりません。

## Open question

gate UI を有効にする前に、次の点を解決する必要があります。

- どの slow password-verifier algorithm/parameter と、private service-held pepper の採否が、
  deployment の security/runtime target を満たすか。
- preview usability と revocation/abuse resistance のバランスを取る signed-capability TTL
  および per-project/per-client verification rate limit はいくつか。
- gate UI を有効にする正確な product milestone はどれか。roadmap は default-off feature
  を M2 に置いていますが、M1 では full security path が完成するまで明示的に保留します。

これらは deferred decision です。承認前に implementation や UI copy が値を暗黙に選択・
約束してはなりません。
