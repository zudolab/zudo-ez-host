## Feature contract

Password protection is configured per project and defaults off. It is a shared
preview gate in front of the entire public site, not an account login. When the
gate is enabled, every content request—including requests for real static
assets—must pass authorization before artifact lookup, byte delivery, or any
cache read.

The project password is never stored in plaintext. The private control boundary
stores a slow, salted per-project verifier and owns any pepper or signing
secret. The multi-tenant public Worker has no password verifier, tenant secret,
shared password secret, signing secret, D1 access, or write capability. It can
only call a narrow private authorization service and verify a returned
capability with a pinned public key.

## Enable, rotate, and disable

The webapp presents explicit project-scoped actions and consequences:

- **Enable:** starting from the default-off state, accept a new shared password,
  derive and store its private per-project verifier, increment the gate epoch,
  and require authorization for all subsequent site requests.
- **Rotate:** replace the verifier, increment the epoch, and invalidate every
  capability issued for the previous epoch. Existing visitors must enter the
  new password.
- **Disable:** remove or deactivate the private verifier, increment the epoch,
  invalidate outstanding capabilities, and return the project to its normal
  public serving and cache policy.

The UI must never display or recover the stored password. It confirms the
project being changed and explains that rotation or disablement ends access
granted by earlier capability cookies. Gate changes affect serving access, not
the immutable project URL or publication artifact.

## Visitor flow

For an enabled gate, the public Worker resolves the exact host and current
project gate state before serving content. A visitor without a current valid
capability receives a platform-owned password form. The narrow login `POST`
sends the submitted password to the private verifier service; nonexistent
projects and wrong passwords receive the same generic denial.

Successful verification returns a short-lived signed capability bound to the
immutable project ID, exact public hostname, current gate epoch, issued and
expiry times, and a random token ID. The public Worker verifies that capability
with its pinned public key and sets it in a host-only `__Host-` cookie with
`Secure`, `HttpOnly`, `Path=/`, and `SameSite=Strict`.

A valid signature alone is insufficient. On every request, current project and
gate authorization is checked before bytes or cache, including that the
capability's host, project, epoch, and time bounds remain current. Password
submission is body-size limited and rate-limited, and comparison uses the
selected slow verifier without exposing whether a project exists.

## Security and cache behavior

Gate-before-bytes and gate-before-cache are release invariants. A successful
visitor must never warm a public response that an unauthenticated visitor can
reuse. V1 therefore bypasses shared cache for every gated response, including
authorized artifact bytes, rather than trying to partition cache entries by
cookie.

Login pages, denial responses, login `POST` responses, and authorized gated
content are `no-store`. Gated artifact responses use both
`Cache-Control: private, no-store` and `CDN-Cache-Control: no-store`; the Worker
does not call `cache.put`, and no cache rule may override that policy. `Vary:
Cookie` is defense in depth, not permission to cache. Platform gate pages and
responses must not echo or log the submitted password and should prevent search
indexing.

Epoch changes provide immediate logical revocation even if an old capability
has not reached its expiry. The public Worker remains secrets-free with respect
to tenant credentials, limiting the impact of a responder compromise.

## Limits of shared-password access

A gate proves only that a visitor knows the project's current shared password
and holds a corresponding short-lived capability. It creates no visitor
account or durable visitor identity. The feature has no visitor roles,
per-person permissions, individual revocation, visitor list, or visitor audit
trail.

Anyone who receives the shared password may pass it on. Rotation revokes the
old shared capability epoch for everyone; it cannot selectively remove one
visitor. Projects that need named collaborators, individual access control, or
auditable access require a different future feature and must not stretch this
gate into that role.

## Open questions

The following points must be resolved before the gate UI is enabled:

- Which slow password-verifier algorithm and parameters, and whether a private
  service-held pepper, meet the deployment's security and runtime targets?
- What signed-capability TTL and per-project/per-client verification rate limits
  balance preview usability with revocation and abuse resistance?
- Which exact product milestone enables the gate UI? The roadmap places the
  default-off feature in M2, while M1 explicitly holds it back until its full
  security path is complete.

These are deferred decisions. Implementations and UI copy must not silently
choose or promise values before they are accepted.
